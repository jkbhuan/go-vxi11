go-vxi/vxi11 接口说明文档

VXI-11（TCP/IP Instrument Protocol）客户端包 · 纯 Go 实现 · 零第三方依赖 · 无 cgo

对应规范：VXI-11 Rev 1.0；RPC 见 RFC 5531，XDR 见 RFC 4506

1. 概述

go-vxi/vxi11 让 Go 程序通过 LAN 控制支持 VXI-11 的仪器（示波器、信号源、万用表等）。 整个包只有几千行，自己实现了从 TCP 到 SCPI 的完整链路，没有任何第三方依赖： 

你的代码
   │  Query("*IDN?") / Write(...) / ReadAll(...)      ← 本包对外 API
   ▼
VXI-11 过程层   create_link / device_write / device_read / ...   (Section C.1)
   │
   ▼
ONC RPC (RFC 5531)   xid、MSG_CALL/MSG_REPLY、AUTH_NULL
   │
   ▼
记录标记 (RFC 5531 §11)   4 字节分片头，最高位 = 最后一片
   │
   ▼
XDR (RFC 4506)   4 字节对齐、长度前缀
   │
   ▼
TCP  +  portmapper(rpcbind) 端口发现 (prog 100000, proc 3 = GETPORT)

设计要点

  • 端口不硬编码：先向 portmapper 查 DEVICE_CORE 的端口，再连过去。
  • 写自动分片：超过 maxRecvSize 的数据自动切成多次 device_write，只有最后一片带 END。
  • 读封装成"读到结束"：Query/ReadAll 循环调用 device_read 直到设备指示 END，避免长响应被截断。
  • 错误可编程判定：设备错误码与本地错误都是可用 errors.Is/errors.As 判定的 Go error。
  • 可测试：内置一个内存假仪器（mock），无需硬件即可端到端跑通全部流程。

包的构成

文件职责
client.go对外 API：Client、Dial、各 Option
protocol.goVXI-11 过程号、结构体编解码、Flags、ReadReason
rpc.goONC RPC over TCP、记录标记、应答解析
xdr.goXDR 编解码器
intr.gointerrupt channel：客户端侧 DEVICE_INTR 服务端、CreateIntrChan/DestroyIntrChan/OnSRQ
errors.go错误码与哨兵错误

2. 快速开始

2.1 引入

模块路径为 go-vxi，包路径 go-vxi/vxi11：

import "go-vxi/vxi11"

若放在自己的仓库里，把 go.mod 的 module 改成实际路径即可，包内无相对导入，不会受影响。

2.2 最小示例

package main

import (
	"fmt"
	"log"
	"time"

	"go-vxi/vxi11"
)

func main() {
	// 1. 连接：portmapper 查端口 -> 建 core channel -> create_link
	c, err := vxi11.Dial("5.5.5.1", "inst0", 5*time.Second)
	if err != nil {
		log.Fatal(err)
	}
	defer c.Close() // 发送 destroy_link 并关闭连接

	// 2. 标准 SCPI 查询
	idn, err := c.Query("*IDN?")
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println(idn)
	// RIGOL TECHNOLOGIES,DS1104Z,DS1ZA212606163,00.04.04.SP4

	// 3. 二进制长响应（IEEE 488.2 定长块，例如屏幕截图）
	data, err := c.QueryBytes(":DISP:DATA?\n", 30*time.Second)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("收到 %d 字节\n", len(data))
}

2.3 连接生命周期

Dial(host, device, timeout, opts...)
 ├─ portmapper GETPORT(prog=0x0607AF, vers=1, prot=TCP)   → core 端口
 ├─ TCP 连接 core 端口
 ├─ create_link(clientId, lockDevice, lockTimeout, device) → lid / abortPort / maxRecvSize
 └─ （可选）TCP 连接 abortPort，作为 abort channel
        │
        ├── Write / WriteString / Query / QueryBytes / Read / ReadAll
        ├── Clear / Trigger / Remote / Local / ReadSTB / Docmd
        ├── Lock / Unlock
        ├── CreateIntrChan → OnSRQ + EnableSRQ → DestroyIntrChan（interrupt channel）
        └── Abort（走 abort channel）
        │
Close()
 ├─ destroy_intr_chan（若 interrupt channel 已建立）
 ├─ destroy_link(lid)
 └─ 关闭 core / abort / intr 所有连接（幂等）
务必 Close Client 持有真实的 TCP 连接与设备端的 link 资源。不调用 Close 会在仪器侧留下悬挂的 link， 仪器通常有 link 数量上限，反复泄漏会让后续连接失败。惯用写法是 defer c.Close()。

4. 选项 Option

Option 是函数式选项，只在 Dial 时生效，用于定制连接行为：

type Option func(*dialConfig) error

全部选项都是可选的，不传即使用默认值。选项返回 error 时 Dial 会立即失败（例如端口号越界）。

WithPortmapperPort

func WithPortmapperPort(port int) Option
参数
port — portmapper 端口，合法范围 1..65535，否则 Dial 返回错误。
默认
111
说明
用于非标准 portmapper 端口，或测试环境。正常仪器不需要。

WithCorePort

func WithCorePort(port int) Option
参数
port — DEVICE_CORE 的 TCP 端口，合法范围 1..65535。
说明
直接连接该端口，跳过 portmapper 查询。
规范建议始终通过 portmapper 发现端口，所以此选项只应用于：仪器没有跑 portmapper、或调试时想锁定端口。

WithClientID

func WithClientID(id int32) Option
参数
id — create_link 上报的 clientId，任意 int32。
默认
随机数（rand.Int31()）
说明
该值只用于设备端调试追踪，不影响协议行为。多进程共用同一台仪器时给它一个可辨识的值有助排查。

WithLockOnCreate

func WithLockOnCreate(lock bool, timeout time.Duration) Option
参数
lock — 是否在 create_link 时直接请求设备锁；
timeout — 等待锁的时长，<= 0 表示不等待（锁被占用即失败）。
默认
false, 0（不锁）
错误
锁被其它 link 占用且未等待时，Dial 返回 *DeviceError{Op:"create_link", Code:ErrDeviceLocked}，可用 errors.Is(err, vxi11.ErrDeviceLocked) 判定。

WithTermChar

func WithTermChar(ch byte) Option
参数
ch — 终止字符。
默认
'\n'
说明
Query / QueryWithTimeout 在读取时会置 termchrset 位并使用该字符作为终止符， 这样即使设备不发 END 指示也能正常收尾。
QueryBytes / Read / ReadAll 不使用终止符，因此对二进制数据安全。
设为 0 表示连 Query 也不使用终止符，完全依赖设备的 END。

WithReadSize

func WithReadSize(n uint32) Option
参数
n — 单次 device_read 请求的字节数，不能为 0（为 0 时 Dial 报错）。
默认
64 KiB（defaultReadSize），内部上限 1 MiB。
说明
设备可以只返回它当前拥有的数据，所以请求大一些不会出错，只会减少往返次数。
若某台设备对 requestSize 特别敏感，可以调小。这个值不是 maxRecvSize——后者只约束写。

WithMaxResponseBytes

func WithMaxResponseBytes(n int) Option
参数
n — 累积响应字节数上限，必须为正数。
默认
DefaultMaxResponseBytes（64 MiB）
错误
超出时 Query/ReadAll 返回 ErrResponseTooLarge，同时返回已读到的部分数据。

WithAbortChannel

func WithAbortChannel(enable bool) Option
参数
enable — 是否在 create_link 之后尝试建立 abort channel。
默认
true
说明
abort channel 是可选的，建立失败不影响正常收发，只会让 Abort 返回 ErrNoAbortChannel。 设备未通告 abortPort 时也不会建立。

WithDialer

func WithDialer(d *net.Dialer) Option
参数
d — 自定义 *net.Dialer（可配置 LocalAddr、KeepAlive 等），不能为 nil。
说明
该 dialer 会被浅拷贝后使用；若其 Timeout 为 0，则用 Dial 的 timeout 参数填充。
注意 Dialer.Context 不会被本包使用（本包通过 socket 截止时间控制超时）。

WithWriteChunkSize

func WithWriteChunkSize(n int) Option
参数
n — 分片大小：
n > 0：每片最多 n 字节，只有最后一片带 END；
n == 0：不分片，整条命令用一次 device_write 发出；
负数：Dial 报错。
默认
不调用 = 跟随 create_link 返回的 maxRecvSize（并夹在 1024..1 MiB 之间）。
说明
规范要求单次 device_write 的数据不超过设备通告的 maxRecvSize，因此默认按它分片。
但要注意：实测部分仪器（如 RIGOL DS1000Z 系列）会把每个 device_write 当成一条完整消息解析， 这时分片会把一条命令拆成多条错误命令，需要用 0 关闭分片（见 §12）。

5. Client 方法

Client 是一条已建立的 VXI-11 link，内部持有 core channel 与可选的 abort channel 两条 TCP 连接。 所有方法都是并发安全的。

type Client struct {
	// 所有字段均未导出，通过方法访问
}

5.1 建立与关闭

Dial MVP

func Dial(host, device string, timeout time.Duration, opts ...Option) (*Client, error)
host
仪器 IP 或主机名，不要带端口（端口由 portmapper 决定）。不能为空。
device
VXI-11 设备名，通常是 "inst0"；空串表示使用 DefaultDevice。
timeout
既作 TCP 连接超时，也作 create_link 的 I/O 超时；<= 0 时用 DefaultTimeout。
返回
新的 *Client；出错时返回 nil 与错误。
错误
连接失败 → ErrTimeout/ErrTransport；
仪器未注册 DEVICE_CORE → ErrPortmapper；
设备名不存在 → ErrDeviceNotAccessible（错误码 3）；
使用 WithLockOnCreate 且锁被占 → ErrDeviceLocked（错误码 11）。

执行三步：portmapper 查端口 → 建 core channel → create_link。成功后按需建立 abort channel。 只要返回的 err == nil，就一定要 Close。

Close MVP

func (c *Client) Close() error
返回
首次调用：destroy_link 的错误（如果失败）；重复调用：nil。
说明
发送 destroy_link，然后关闭 core 与 abort 两条连接。
  • 幂等：重复调用只返回 nil，可以安全地 defer + 手动各调一次。
  • 连接一定会被关闭：即使 destroy_link 失败（例如设备已经掉线），两条 TCP 连接也会被释放， 不会泄漏 socket 或 goroutine。此时把 destroy_link 的错误返回给调用方记录即可。
  • Close 之后所有方法返回 ErrClosed（Close 自身除外）。
  • 若 destroy_link 超时，内部使用 DefaultTimeout，不会无限等待。

5.2 写入

Write MVP

func (c *Client) Write(data []byte, ioTimeout time.Duration) (int, error)
data
要写入的原始字节（SCPI 命令或二进制块）。
ioTimeout
设备侧 I/O 超时；<= 0 使用客户端默认超时。
返回
n — 设备实际接收的字节数（正常时等于 len(data)）；
err — 出错时的错误，此时 n 是已经成功写入的部分字节数。
错误
ErrShortWrite（设备报告写入字节数少于提交量）；
*DeviceError（错误码 5 参数错误、11 设备被锁等）；
ErrTimeout/ErrTransport/ErrConnBroken。

若 len(data) 超过设备通告的 maxRecvSize，会自动分片发送，只有最后一片带 END 标志 （规范 Section C.1：end 表示"本条消息的最后一个字节"）。分片大小见 WithWriteChunkSize。

n, err := c.Write([]byte("*CLS\n"), 0)
if err != nil { log.Fatal(err) }
fmt.Println(n)  // 5

WriteString MVP

func (c *Client) WriteString(cmd string) error
cmd
SCPI 命令文本。
返回
仅 error。
说明
若 cmd 未以 "\n" 结尾会自动补上（已结尾则不会重复添加）。使用默认超时。

5.3 读取

Read

func (c *Client) Read(maxLen int, ioTimeout time.Duration) ([]byte, error)
maxLen
本次最多读取的字节数；<= 0 表示使用默认请求长度（见 WithReadSize）。
返回
本次 device_read 拿到的数据。
说明
只执行一次 device_read，不设置终止符（二进制安全）。
返回的数据量可能小于请求量——设备返回多少就是多少。
不要用 Read 读长响应 一次 Read 对应一次 RPC。:DISP:DATA? 这类上百 KB 的响应需要反复读， 用 ReadAll 或 QueryBytes 才会自动读到结束。

ReadWithReason

func (c *Client) ReadWithReason(maxLen int, ioTimeout time.Duration) ([]byte, ReadReason, error)
返回
除数据外还返回设备给出的 reason 位（ReasonReqCnt/ReasonChr/ReasonEnd，见 §8.3）。
说明
需要自己实现读取循环时用这个，可以精确判断"缓冲区读满"与"消息结束"的区别。

ReadAll MVP

func (c *Client) ReadAll(maxLen int, ioTimeout time.Duration) ([]byte, error)
maxLen
累积读取的上限；<= 0 表示只用客户端的 maxResponse 上限。
返回
多次 device_read 拼接后的完整数据。出错时返回的 data 可能包含已成功读取的部分数据。
错误
ErrResponseTooLarge（达到上限）；ErrProtocol（连续太多次仍未读到结束标志）。

反复调用 device_read 直到满足结束条件之一：

  • 设备返回 reason 含 END（消息结束）或 CHR（命中终止符）；
  • 本次读到 空数据（设备没有更多内容了）；
  • 累积字节数达到上限。

不设置终止符，二进制安全。这是处理长响应的正确方式。

5.4 查询

Query MVP

func (c *Client) Query(cmd string) (string, error)
cmd
SCPI 查询命令，如 "*IDN?"。未以 "\n" 结尾会被自动补上。
返回
应答文本，已去掉结尾的 CR/LF。
说明
等价于 Write(cmd) + ReadAll，两步在同一个锁内完成， 因此并发调用时各 goroutine 拿到的是自己那次查询的应答。
注意
读取时启用终止符 '\n'，返回 string。二进制数据请用 QueryBytes。
idn, err := c.Query("*IDN?")
freq, err := c.Query(":CHAN1:SCAL?")

QueryWithTimeout

func (c *Client) QueryWithTimeout(cmd string, ioTimeout time.Duration) (string, error)
说明
与 Query 相同，但可以指定 I/O 超时。
用于耗时较长的查询，例如 :DISP:DATA? 之前的 MEAS:... 类操作。

QueryBytes MVP

func (c *Client) QueryBytes(cmd string, ioTimeout time.Duration) ([]byte, error)
cmd
命令，会被原样发送（不自动补 '\n'，需要时自行拼上）。
返回
原始应答字节，不做任何裁剪。
说明
与 Query 的唯一区别是不设置终止符、返回字节切片， 适用于 :DISPLAY:DATA? 这类 IEEE 488.2 定长块应答。
data, err := c.QueryBytes(":DISP:DATA?\n", 30*time.Second)
// data 形如  #9001152054<1152054 字节的位图>

5.5 通用操作

以下方法都是"无返回数据、只有错误码"的 VXI-11 过程，成功返回 nil，失败返回 *DeviceError。 都使用客户端默认超时。

方法对应过程作用
Clear() errordevice_clear (15) 清空设备的输入/输出缓冲并复位待处理的操作。MVP
Trigger() errordevice_trigger (14) 触发一次设备操作，等价于 SCPI 的 *TRG。
Remote() errordevice_remote (16) 让设备进入远程控制状态。
Local() errordevice_local (17) 让设备回到本地控制状态，与 Remote 相反。
ReadSTB() (byte, error)device_readstb (13) 读取状态字节（Status Byte），等价于 SCPI 的 *STB?。
实测 RIGOL DS1000Z 返回错误码 8（不支持），改用 Query("*STB?")。
EnableSRQ(enable bool, handle []byte) errordevice_enable_srq (20) 启用/禁用 SRQ 中断上报。handle 是中断通道句柄，最大 40 字节，超出直接返回本地错误。
要真正收到 SRQ 通知，需先调用 CreateIntrChan 建立 interrupt channel。
Docmd(cmd int32, networkOrder bool, datasize int32, data []byte, ioTimeout time.Duration) ([]byte, error)device_docmd (22) 执行设备相关命令。cmd 取值由厂商定义；networkOrder 表示本机是否大端 （x86/ARM 常见系统传 false）；datasize 是 data 中单个元素的字节数 （1 = 不透明字节流）。返回设备的 data_out。
设备不支持该 cmd 时返回错误码 8。典型用途是 GPIB 网关控制，LAN 示波器一般返回错误码 8。
CreateIntrChan() errorcreate_intr_chan (25) 在本机随机端口启动 DEVICE_INTR 服务端（IPv4/TCP），并把地址通过 create_intr_chan 告知设备； 重复调用幂等。设备不支持时返回错误码 8/6。建立后用 OnSRQ + EnableSRQ 接收 SRQ。
DestroyIntrChan() errordestroy_intr_chan (26) 让设备关闭 interrupt channel 并停止本机服务端；幂等。Close 会自动调用。
OnSRQ(h func(handle []byte))device_intr_srq (30, 设备→客户端) 设置 SRQ 回调；handle 即 EnableSRQ 登记的内容。传 nil 取消。 回调在服务端 goroutine 里执行，应尽快返回。

5.6 锁

Lock MVP

func (c *Client) Lock(timeout time.Duration) error
timeout
> 0：置 waitlock 位并等待最多该时长（毫秒精度）；
<= 0：不等待，锁被占用立刻返回错误码 11。
错误
锁被其它 link 持有 → errors.Is(err, vxi11.ErrDeviceLocked)。
说明
自动把 socket 截止时间放宽 timeout，否则等锁会先撞上 I/O 超时。

Unlock MVP

func (c *Client) Unlock() error
错误
本 link 未持锁 → 错误码 12 ErrNoLockHeld。

锁是 link 级别的：link 被销毁（Close）时设备会释放它持有的锁。

5.7 abort channel

Abort

func (c *Client) Abort() error
返回
成功 nil；设备不支持该过程时 ErrOperationNotSupported（错误码 8）。

6. 错误处理

本包的错误分两类，两者都支持 errors.Is / errors.As：

  • 设备错误码：仪器在响应报文的 error 字段里返回的 VXI-11 错误码（规范 Table B.2）。
  • 本地错误：传输层 / XDR 层 / 客户端自身产生的哨兵错误，不会出现在报文里。

6.3 判定范式

import (
	"errors"
	"log"

	"go-vxi/vxi11"
)

_, err := c.Query(":FOO:BAR?")
switch {
case err == nil:
	// 正常

case errors.Is(err, vxi11.ErrDeviceLocked):
	// 错误码 11：别的 link 占了锁。等一下或放弃。
	log.Println("设备被占用")

case vxi11.IsTimeout(err):
	// 网络层超时 或 设备返回错误码 15
	log.Println("超时")

case errors.Is(err, vxi11.ErrConnBroken):
	// 连接已熔断，必须重新 Dial
	log.Println("连接失效，需要重连")

case errors.Is(err, vxi11.ErrOperationNotSupported):
	// 仪器不支持该操作，降级处理

default:
	// 取出过程名与错误码，写日志
	var de *vxi11.DeviceError
	if errors.As(err, &de) {
		log.Printf("设备错误: op=%s code=%d (%s)", de.Op, int32(de.Code), de.Code)
	} else {
		log.Printf("错误: %v", err)
	}
}
好消息：设备错误不会污染连接 设备返回错误码只说明本次操作失败，TCP 连接与 link 都还是好的，可以继续用（例如 :SYST:ERR? 查错后再重试）。 只有传输层错误（ErrConnBroken 等）才需要重新 Dial。

7. 关键语义

7.1 写入分片

规范规定单次 device_write 的数据不得超过设备在 create_link 响应里通告的 maxRecvSize （规范保证它至少为 1024）。本包默认行为：

Write(data)  ──►  按 chunk 切分，逐片 device_write
                  chunk = maxRecvSize（夹在 1024 .. 1 MiB 之间）

  片 1        flags = 0        （无 END）
  片 2        flags = 0
  片 3        flags = FlagEnd  （只有最后一片带 END）

end 标志的含义是"本条消息的最后一个字节"，所以只有最后一片能带它。 若中途某片出错，Write 返回已经写入的字节数与错误，此时设备侧收到的是一条不完整的消息。

有些仪器把每个 device_write 当成一条完整消息 这类仪器（实测 RIGOL DS1000Z 系列即如此）在收到分片时会逐片解析，导致一条命令被拆成若干条错误命令。 对它们必须用 WithWriteChunkSize(0) 关闭分片。
判断方法：分片写入后查 :SYST:ERR?，若出现 -101,"Invalid character" 之类的语法错误， 而同样的命令不分片就正常，那就是这个原因。

7.2 长响应拼接

规范 OBSERVATION B.6.9 明确指出：一次 device_read 可能返回了数据，但 reason 全为 0—— 设备内部缓冲满了，它先把这些给你。此时必须继续读，否则长回复会被截断。

ReadAll / Query 的循环：

  ┌─► device_read(requestSize)
  │      │
  │      ├─ 返回数据为空 ────────────────► 结束（设备没更多了）
  │      ├─ reason 含 END 或 CHR ───────► 结束（消息完整）
  │      ├─ 累积长度 >= 上限 ───────────► ErrResponseTooLarge
  │      └─ reason == 0 或只有 REQCNT ──┐
  └──────────────────────────────────────┘  继续读

实测 RIGOL DS1104Z 读 1,152,066 字节的 :DISP:DATA? 屏幕数据，需要约 18 次 device_read 才能拼完，只有循环读才能拿到完整的 IEEE 488.2 定长块。

7.3 超时模型

一次调用涉及两个超时，本包分别设置：

层值作用
设备侧 io_timeout调用方给的 ioTimeout（毫秒精度写入报文） 告诉仪器：这次操作最多等多久，超时请返回错误码 15。
socket 截止时间socketTimeout(ioTimeout) 告诉本机 TCP 栈：多久没数据就报错。
func socketTimeout(d time.Duration) time.Duration {
	if d <= 0 { return 0 }          // 0 = 不设截止时间
	margin := d/2 + 100*time.Millisecond
	if margin > time.Second { margin = time.Second }
	return d + margin
}

socket 超时故意比设备侧超时长一点，这样设备有机会用自己的逻辑返回错误码 15（一条干净的协议应答）， 而不是被客户端直接掐断连接、把 TCP 字节流搞乱。余量取 d/2 + 100ms，上限 1 秒， 使短超时也能被如实反映出来（例如 200ms 的超时不会变成 1.2 秒）。

因此一次超时可能表现为两种错误：

  • 设备先超时 → ErrIOTimeout（错误码 15），连接保持完好；
  • 网络先断 → ErrTimeout（本地），该通道被标记为 ErrConnBroken。

用 vxi11.IsTimeout(err) 可以同时捕获这两种情况。

7.4 并发

  • Client 的所有方法都是并发安全的。
  • 对 core channel 的调用被一把互斥锁串行化；Query 的 write + read 在同一个锁内完成， 所以多个 goroutine 并发 Query 不会串台——各自拿到自己那次查询的应答。
  • Abort 使用独立的连接和独立的锁，因此不会被正在进行的长时间读写阻塞， 这正是 abort channel 存在的意义。
  • getter（Port()、LinkID() 等）读取的是建链后不再变化的字段，无需加锁。
  • VXI-11 是请求-应答协议，同一 link 上不能流水线发包，所以串行化不会带来额外损失。
一个 link = 一个逻辑会话 同一台仪器可以被多个进程/多个 link 同时连接，但它们共享仪器的输出缓冲。 若需要保证一段操作序列不被打断，用 Lock / Unlock 显式加锁。

8.2 标志位 Flags

type Flags uint32

const (
	FlagWaitLock   Flags = 1 << 0  // bit0 waitlock   : device_lock 时锁被占则等待而非报错 11
	FlagEnd        Flags = 1 << 3  // bit3 end        : device_write 的最后一个字节带 END 指示
	FlagTermChrSet Flags = 1 << 7  // bit7 termchrset : device_read 使用 TermChar 作为终止符
)

func (f Flags) String() string  // "waitlock|end|termchrset"，0 时为 "0"

8.3 读取 reason 位 ReadReason

type ReadReason int32

const (
	ReasonReqCnt ReadReason = 1 << 0  // bit0 REQCNT : 已读满本次请求的字节数，可能还有更多数据
	ReasonChr    ReadReason = 1 << 1  // bit1 CHR    : 读到终止符（仅在置了 termchrset 时有意义）
	ReasonEnd    ReadReason = 1 << 2  // bit2 END    : 消息结束
)

func (r ReadReason) Has(bit ReadReason) bool  // 判断某位是否置位
func (r ReadReason) String() string
关键：reason == 0 不是结束 设备可能返回了数据但 reason 全为 0，此时必须继续读（见 §7.2）。 只有 END / CHR / 空数据才算读完。

8.4 XDR 与记录标记

XDR（RFC 4506）编码规则

  • 所有数据按 4 字节对齐，不足补 0。
  • int32 / uint32：大端 4 字节。
  • bool：4 字节（0 / 1），不是 1 字节。
  • unsigned short / char：在报文里同样是 4 字节（TermChar 也是 4 字节）。
  • 变长 opaque<> / string<>：4 字节长度前缀 + 数据 + 补零到 4 字节边界。
  • 字符串没有 '\0' 结尾，长度就是长度。

记录标记（RFC 5531 §11）

每条 RPC 消息前面加一个 4 字节头（大端 uint32）：

  bit31 = 1  最后一片（last fragment）
  bit31 = 0  后面还有分片
  bit0..30   本片的数据长度（<= 0x7FFFFFFF）

本包把一整条消息的所有分片合并在一次 Write 里发出（只有一片，置 bit31），
读取时会循环收集分片直到遇到置了 bit31 的那片。

VXI-11 结构体的字段顺序（规范 Section C.1）

// Create_LinkParms
int32 clientId; bool lockDevice; uint32 lock_timeout; string device;

// Create_LinkResp
Device_ErrorCode error; int32 lid; uint16 abortPort; uint32 maxRecvSize;

// Device_WriteParms
int32 lid; uint32 io_timeout; uint32 lock_timeout; Device_Flags flags; opaque data<>;

// Device_WriteResp
Device_ErrorCode error; uint32 size;

// Device_ReadParms
int32 lid; uint32 requestSize; uint32 io_timeout; uint32 lock_timeout;
Device_Flags flags; char termChar;

// Device_ReadResp
Device_ErrorCode error; int32 reason; opaque data<>;

// Device_GenericParms（注意字段顺序）
int32 lid; Device_Flags flags; uint32 lock_timeout; uint32 io_timeout;

// Device_LockParms            // Device_Link
int32 lid; Device_Flags flags; uint32 lock_timeout;   int32 lid;

Device_GenericParms 的字段顺序是 lid, flags, lock_timeout, io_timeout， 与 Device_WriteParms 的 lid, io_timeout, lock_timeout, flags 不同， 两者很容易写反，本包用独立的结构体分别编解码。

12. 真机实测记录

以下数据来自对 RIGOL DS1104Z（IP 5.5.5.1）的实测，可作为排查类似仪器的参考。

建链结果

portmapper GETPORT(prog=0x0607AF, vers=1, prot=TCP)  →  端口 618
create_link(clientId=随机, lockDevice=false, device="inst0")
  ├─ lid          = 0
  ├─ maxRecvSize  = 1500
  └─ abortPort    = 619

*IDN?  →  RIGOL TECHNOLOGIES,DS1104Z,DS1ZA212606163,00.04.04.SP4

现象与结论

现象结论 / 处理
device_readstb 返回错误码 8（operation not supported） 该机型不支持此过程，改用 Query("*STB?")。集成测试里对此 Skip 而非判失败。
通告了 abortPort=619，但 device_abort 也返回错误码 8 通告归通告，实际不支持。Abort 会返回 ErrOperationNotSupported。
一次 device_write 发送 3006 字节（> maxRecvSize=1500）→ 错误码 5 证明必须按 maxRecvSize 分片。本包的默认行为正是如此。
分片写入 3006 字节后 :SYST:ERR? 报 -101,"Invalid character" 定位后确认不是分片造成的，而是载荷本身以 "*CLS;\n" 结尾——; 后面直接跟消息终止符是非法 SCPI。 改成 "*CLS;" 重复 + 最后一条带 \n 后错误队列为 0,"No error"。
读 1,152,066 字节的 :DISP:DATA? 用 requestSize = maxRecvSize = 1500 需要 72 秒； 改成 64 KiB 只需 3.4 秒（约 21 倍）。这就是 defaultReadSize = 64 KiB 的由来。
返回的定长块头为 #9001152054，声明 1,152,054 字节，与实际收到的数据一致。
对同类仪器的两点建议
  1. 先做一次小规模实测确认仪器是否接受分片写入，不接受就用 WithWriteChunkSize(0)。
  2. 读大块二进制数据时用 QueryBytes 而不是 Query——前者不设终止符，二进制安全。

Tektronix MSO58（IP 10.42.71.185）

portmapper GETPORT(prog=0x0607AF, vers=1, prot=TCP)  →  端口 7000
create_link(device="inst0")
  ├─ lid          = -1161953280
  ├─ maxRecvSize  = 4096
  └─ abortPort    = 7001

*IDN?  →  TEKTRONIX,MSO58,B014368,CF:91.1CT FV:2.12.5.2206
现象结论 / 处理
device_readstb 正常返回状态字节 0x00；锁、device_clear、device_trigger 均正常 核心功能完整可用。
:SYST:ERR? 查询读超时（设备错误码 15） 该机不支持该命令，错误队列用泰克的 ALLEv?。注意：不认识的查询不会产生任何响应， device_read 会一直等到设备侧超时——新仪器先用 *IDN? 验证命令。
:DISP:DATA? 读超时 不支持。截图走 SAVe:IMAGe "C:/Temp/screen.png" + FILESystem:READFile 'C:/Temp/screen.png'，实测读回 206,827 字节裸 PNG（非定长块），耗时约 10 ms。
8200 字节写入按 maxRecvSize=4096 分 3 片，错误队列无报错 该机接受分片 device_write（与 RIGOL DS1000Z 不同）。
通告 abortPort=7001，但 device_abort 无在途操作时返回错误码 4 （invalid link identifier），有在途 device_read 时不应答（网络超时） abort channel 是坏的（lid 明明有效却报 invalid link identifier，且不能中断在途读）。 需要中断操作时建议直接 Close 后重新 Dial。集成测试对此 Skip。
interrupt channel 全链路实测通过 CreateIntrChan → EnableSRQ(true, handle) → 写 *ESE 1; *SRE 32; *OPC → 收到 device_intr_srq 回调，handle 原样带回。
device_docmd（cmd=0）返回错误码 8 预期行为：该机不支持任何 docmd 命令。
